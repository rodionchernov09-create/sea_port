# Sea Port Simulation: подробное руководство по устройству проекта

Этот документ описывает фактическую реализацию в `include/`, `src/` и `frontend/`.
Приложение написано на C++20. Под «бэкендом» здесь понимается доменная библиотека
`sea_port_lib`, а не сетевой сервер: HTTP, базы данных и отдельного серверного
процесса в проекте нет. «Фронтенд» — настольное окно GLFW/OpenGL/Dear ImGui.
Консольный интерфейс в `src/main.cpp` — ещё один клиент библиотеки.

## 1. Карта проекта и сборка

```text
SeaPortSimulation/
├── CMakeLists.txt                 # три цели и интеграционный тест
├── include/sea_port/             # публичный API доменной модели
│   ├── types.h                   # типы данных между слоями
│   ├── sea_port.h                # базовая физическая сущность
│   ├── cargo.h, ship.h, crane.h # грузы, суда, краны
│   ├── ship_queue.h              # собственная односвязная очередь
│   ├── weather.h                 # преобразование высоты волн
│   ├── random_generator.h        # детерминированная случайность
│   ├── statistics.h              # накопление результатов
│   ├── port_simulation.h         # оркестратор одного месяца
│   └── crane_optimizer.h         # пакетный экономический поиск
├── src/                          # определения бэкенда и консольный main
├── frontend/main.cpp             # окно, формы, команды, отчёты
├── frontend/port_view.h/.cpp     # визуальная проекция порта
├── tests/integration_test.cpp    # проверка доменной модели
├── external/glfw, external/imgui # сторонние зависимости
└── docs/                         # описание и формулы
```

`CMakeLists.txt` задаёт C++20 и библиотеку `sea_port_lib` из десяти файлов `src/`.
Цель `sea_port` собирает консольный клиент, `sea_port_gui` — графический клиент.
Последняя цель включена по умолчанию и требует OpenGL и GLFW; если системный GLFW
не найден, используется подпроект `external/glfw`. ImGui включён непосредственно
исходниками из `external/imgui`. Цель `integration_test` и `ctest` включаются через
стандартный `BUILD_TESTING` CMake. Все три программы используют одну доменную
библиотеку, поэтому GUI не содержит отдельной копии бизнес-правил.

```bash
git submodule update --init --recursive
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/sea_port_gui
./build/sea_port --auto --seed 123
```

Для системы без графических библиотек доступен `-DSEA_PORT_BUILD_GUI=OFF`.
Запуск CLI без параметров интерактивный; `--auto` моделирует месяц с настройками
по умолчанию, `--optimize` запускает экономический перебор, `--seed N` задаёт
начальное состояние генератора. В текущей реализации интерактивная функция
`RunInteractive()` сама создаёт конфигурацию, поэтому переданный через CLI `--seed`
на этот режим не влияет; в автоматическом и оптимизационном режимах он действует.

### Граница слоёв

```text
поля ImGui / аргументы CLI
          │
          ▼
SimulationConfig, ShipSpec, Weather
          │
          ▼
PortSimulation ──► ShipQueue / Ship / Crane / RandomGenerator / Statistics
          │
          ├──► DailyReport, Statistics (цифры и события)
          └──► VisualSnapshot: vector<ShipView> (снимок для рисования)
                   │
                   ▼
              PortView + ImGui
```

Внешний интерфейс обращается к модели командами: создать, запланировать судно,
задать погоду, сгенерировать параметры, продвинуть день, завершить. Возвращаемые
отчёты и снимок состоят из значений, строк и идентификаторов; фронтенд не получает
владение над объектами судов или кранов. Это сохраняет единый источник истины.

## 2. Бэкенд: данные и жизненный цикл

### 2.1 Общие перечисления и структуры (`include/sea_port/types.h`)

`EntityType` различает физические сущности `kShip` и `kCrane`. `CargoType`
использует индексы 0, 1, 2 для сыпучего, жидкого и контейнерного грузов;
`kCount` — служебная граница, а `kCargoTypeCount` — размер массивов.
`CargoIndex(type)` преобразует тип груза в индекс. `Season` задаёт зимний,
весенний, летний и осенний профиль погоды. `ShipState` описывает состояния
`kScheduled`, `kWaiting`, `kUnloading`, `kCompleted`, `kAbandoned`, `kRejected`.
`ToString(CargoType)`, `ToString(Season)` и `ToString(ShipState)` дают строки для
отчёта; неизвестное значение вызывает `invalid_argument`.

`Weather` хранит уровень волн 0–5, работоспособность от 0 до 1 и флаг шторма.
Это значение на один день, не метеорологический прогноз. При автоматическом
получении поле `operability` определяется уровнем волн; заданная вручную погода
может иметь иной коэффициент, если он проходит проверку в `SetWeather()`.

`SimulationConfig` — набор правил одного прогона. `simulation_days` по умолчанию
равен 30; `step_days` задаёт контрольные точки вывода от 1 до 3, а сам расчёт
остаётся дневным. Массивы `crane_counts` и `unloading_places` индексируются
`CargoType`; краны и места — разные ограничения. `waiting_capacity` — общая
вместимость всех трёх очередей. Диапазоны `arrival_deviation_*` и
`unloading_delay_*` управляют случайным сдвигом прибытия и задержкой завершения.
`penalty_per_extra_day` — ставка штрафа за превышение плановой стоянки.
`current_day_arrival_rate` и `future_arrival_decay` задают поток заявок.
`fairness_wait_days` и `waiting_priority_bonus` влияют на порядок выбора.
`minimum_rating_for_optimization` и `minimum_service_rate_for_optimization` —
ограничения поиска. `crane_purchase_cost` — цены трёх типов кранов;
`random_seed` делает сценарий воспроизводимым при одинаковом порядке вызовов.

`ShipSpec` — заявка, а не судно в очереди. Она содержит тип груза, имя, день
регистрации, плановый день прибытия, массу, плановую стоянку и допустимое ожидание.
Поля `actual_arrival_day` и `unloading_delay_days` опциональны: при отсутствии
генерируются в `ScheduleShip()`. Фиксированные значения позволяют создавать
повторяемые сценарии и тесты. День прибытия может оказаться за пределами месяца:
тогда судно останется среди запланированных и не прибудет в этом прогоне.

`ShipView` — компактная копия для карты: стабильный `id`, имя, тип, состояние,
индекс причала (`-1` для ожидающего), масса всего и остаток. Имя не служит ключом:
двум судам разрешено иметь одинаковое название. `DailyReport` хранит результат
одного дня: погоду, количества событий, длину очереди и число разгрузок, дневной
финансовый результат, рейтинг, текстовые события, списки очередей и операций,
а также `departures` для анимации ухода. `CompletionRecord` содержит детальную
финансовую запись только о завершённой разгрузке: плановые/фактические даты,
ожидание, длительность, дополнительные дни, начисление, штраф и чистый результат.

### 2.2 Владение памятью

`PortSimulation` владеет всеми кранами через `vector<unique_ptr<Crane>>`.
После `ScheduleShip()` он владеет судном в `scheduled_ships_`; при прибытии
`unique_ptr<Ship>` переносится в соответствующий `ShipQueue`. При назначении
крана переносится в `ActiveUnloading`. По окончании операции запись
`CompletionRecord` копирует нужные данные, а удаление активной операции
освобождает объект судна. Невладеющий `Crane*` внутри `ActiveUnloading` безопасен,
пока жив `PortSimulation`: сами объекты кранов находятся в выделенной памяти,
и перемещение их `unique_ptr` в векторе не меняет адресов кранов.

`ShipQueue` владеет узлами через `unique_ptr<Node>`, а `tail_` лишь ускоряет
добавление. Копирование очереди запрещено. Графический слой хранит только
`ShipView`, а не указатели в доменную модель. `DailyReport` и `VisualSnapshot()`
можно оставить после следующего дня: это независимые значения, хотя они уже
описывают прошлое состояние.

### 2.3 Жизнь одной заявки

1. `ScheduleShip()` проверяет спецификацию, выбирает фактический день и задержку,
   создаёт конкретный `Ship`, помещает его в список расписания и возвращает ID.
2. В `ProcessArrivals()` наступивший день переносит судно в очередь типа груза.
   При полной общей парковке оно получает `kRejected` и попадает в `departures`.
3. `ProcessAbandonments()` удаляет из очереди суда, у которых истекло терпение.
4. `AssignWaitingShips()` выбирает максимальный приоритет для свободного крана
   и свободного места разгрузки того же типа; судно становится `kUnloading`.
5. `ProcessUnloading()` вычитает дневную производительность с учётом погоды.
   После снятия дополнительной задержки создаёт `CompletionRecord`, освобождает
   кран и удаляет активную операцию.
6. `Finalize()` фиксирует число оставшихся в очередях и активной работе. Оно
   не завершает их искусственно и не начисляет за них доход.

Важная тонкость: каждый день назначение идёт **до** разгрузки. Кран, который
освободился при окончании операции сегодня, сможет принять новое судно только
на следующем дне. Вновь назначенный кран в тот же день уже обрабатывает груз.
Это определяет даты в `CompletionRecord` и видимый темп графика.

## 3. Бэкенд: классы и функции

### 3.1 `SeaPort` (`sea_port.h`, `src/sea_port.cpp`)

Абстрактная база для физических сущностей порта. Содержит `id_` и `name_`.
Конструктор `SeaPort(id, name)` отклоняет нулевой ID и пустое имя. Виртуальный
деструктор позволяет уничтожать наследников через указатель на базу.
Копирование запрещено, перемещение разрешено. `id()` возвращает неизменяемую
идентичность; `name()` возвращает константную ссылку без копирования строки.
Чисто виртуальная `entity_type()` требует от судна и крана вернуть свой тип.
База не хранит состояние всего порта: этим занимается `PortSimulation`.

### 3.2 `Cargo` и три груза (`cargo.h`, `src/cargo.cpp`)

Абстрактный `Cargo` хранит массу и ставку дохода за тонну. Конструктор
`Cargo(weight_tons, revenue_per_ton)` проверяет положительность параметров.
`weight_tons()` и `revenue_per_ton()` читают поля. `base_revenue()` умножает
массу на ставку; это сумма до коэффициента ожидания и штрафа. Чисто виртуальные
`type()` и `name()` различают конкретный груз. Копирование запрещено, деструктор
виртуальный, поскольку владение обычно проходит через `unique_ptr<Cargo>`.

| Класс | Конструктор и ставка | `type()` | `name()` |
|---|---|---|---|
| `GrainCargo` | принимает массу, передаёт ставку 45 | `kBulk` | `grain` |
| `OilCargo` | принимает массу, передаёт ставку 80 | `kLiquid` | `oil` |
| `ContainerCargo` | принимает массу, передаёт ставку 110 | `kContainer` | `containers` |

`CreateCargo(type, weight_tons)` — фабрика: выбирает конкретный класс и
возвращает `unique_ptr<Cargo>`; для служебного `kCount` или неизвестного типа
выбрасывает `invalid_argument`. Сейчас судовые классы прямо создают свой вид
груза, а фабрика оставлена частью публичного API и полезна другим клиентам.

### 3.3 `Ship` и три судна (`ship.h`, `src/ship.cpp`)

`Ship` наследуется от `SeaPort` и владеет одним `Cargo`. Конструктор принимает
ID, имя, даты регистрации/прибытия, плановую стоянку, терпение, задержку и груз.
Проверяет положительность дат и стоянки, неотрицательность терпения и задержки,
наличие груза. `entity_type()` возвращает `kShip`. Чисто виртуальные
`ship_type_name()` и `supported_cargo_type()` конкретизируются наследниками.

| Метод | Точное назначение |
|---|---|
| `booking_day()` | День регистрации заявки; важен для проверки фактического прибытия. |
| `planned_arrival_day()` | Заявленный день прихода, используемый в отчёте. |
| `actual_arrival_day()` | День, когда судно должно перейти из расписания в очередь. |
| `planned_stay_days()` | Допустимая общая стоянка до штрафа. |
| `max_wait_days()` | Число дней ожидания до ухода из очереди. |
| `unloading_delay_days()` | Дополнительная задержка после окончания физической разгрузки. |
| `unloading_start_day()` | Дата назначения крана, изначально 0. |
| `state()` | Текущее состояние автомата судна. |
| `cargo()` | Константный доступ к принадлежащему судну грузу. |
| `potential_revenue()` | Базовая стоимость груза через `Cargo::base_revenue()`. |
| `set_state(state)` | Меняет состояние; порядок переходов обеспечивается оркестратором. |
| `set_unloading_start_day(day)` | Запоминает начало, отвергает день до фактического прибытия. |

`BulkCarrier(id, spec, arrival, delay)` создаёт `GrainCargo` и возвращает
`bulk` из `ship_type_name()`, `kBulk` из `supported_cargo_type()`.
`Tanker` делает то же для `OilCargo`, строки `tanker` и `kLiquid`.
`ContainerShip` делает то же для `ContainerCargo`, строки `container` и
`kContainer`. У всех трёх масса, имя и плановые данные берутся из `ShipSpec`.
`CreateShip()` выбирает один из трёх классов по `spec.cargo_type` и отдаёт
`unique_ptr<Ship>`; некорректный тип приводит к `invalid_argument`.

### 3.4 `Crane` и три крана (`crane.h`, `src/crane.cpp`)

`Crane` тоже наследуется от `SeaPort`. Конструктор принимает тип груза и базовую
производительность, отвергает `kCount` и неположительную производительность.
`entity_type()` возвращает `kCrane`. Чисто виртуальная `crane_type_name()`
задаёт подпись специализации.

| Метод | Точное назначение |
|---|---|
| `cargo_type()` | Тип груза, который кран может разгружать. |
| `base_throughput_tons_per_day()` | Номинальные тонны за сутки при полной работоспособности. |
| `DailyThroughput(weather)` | Ноль при волнах ≥5, иначе номинал × ограниченная диапазоном [0,1] работоспособность. |
| `is_busy()` | Есть ли закреплённый ID судна. |
| `assigned_ship_id()` | Возвращает `optional<ID>` закреплённого судна. |
| `Assign(ship_id)` | Занимает свободный кран; при повторном назначении бросает `logic_error`. |
| `Release()` | Сбрасывает назначение и делает кран свободным. |

`BulkCrane` создаётся с 1800 т/день, возвращает строку `bulk cargo crane`.
`LiquidCrane` — 2400 т/день и `liquid cargo crane`; `ContainerCrane` —
1200 т/день и `container crane`. Их конструкторы фиксируют соответствующий
`CargoType`. Счётчик кранов в конфигурации влияет и на пропускную способность,
и на цену покупки, но не увеличивает число причалов.

### 3.5 `ShipQueue` (`ship_queue.h`)

Очередь реализована вручную как односвязный список. `Node` владеет одним
`unique_ptr<Ship>` и следующим узлом, `head_` владеет цепочкой, `tail_` —
невладеющий адрес последнего узла, `size_` — размер. Конструктор и деструктор
по умолчанию; копирование запрещено, перемещение разрешено.

| Метод | Поведение, крайние случаи и сложность |
|---|---|
| `empty()` | Проверяет отсутствие головного узла; O(1). |
| `size()` | Возвращает сохранённое число узлов; O(1). |
| `Push(ship)` | Передаёт владение в новый хвост; `nullptr` запрещён; O(1). |
| `Pop()` | Извлекает голову и передаёт владение вызывающему; на пустой очереди `nullptr`; O(1). |
| `ExtractBest(score)` | Обходит все узлы, сравнивает численные оценки и извлекает максимум; при равенстве остаётся более раннее судно; O(n). |
| `RemoveIf(predicate)` | Удаляет все подходящие узлы, возвращает их суда в векторе; правильно обновляет голову, хвост и размер; O(n). |
| `ForEach(visitor)` | Вызывает читателя для каждого судна в порядке цепочки; O(n). |

`ExtractBest()` не сортирует очередь постоянно: приоритет зависит от текущего
дня и потому вычисляется при назначении. `RemoveIf()` нужен для ухода по сроку
ожидания. Этот класс не знает о погоде, доходе, причалах и правилах отказа;
такие решения принадлежат `PortSimulation`.

### 3.6 `RandomGenerator` (`random_generator.h`, `src/random_generator.cpp`)

Конструктор `RandomGenerator(seed)` создаёт `mt19937_64`. Генератор хранит
собственное состояние: один и тот же seed даёт одинаковую последовательность
только при одинаковом порядке вызовов. `generated_ship_number_` присваивает
автоматическим заявкам имена `AUTO-0001`, `AUTO-0002` и далее. Идентификатор
судна при этом назначается отдельно в `PortSimulation` и никогда не выводится
из имени.

| Функция | Что именно делает |
|---|---|
| `GenerateWeather(season)` | Берёт дискретное распределение уровней волн для сезона, вытягивает уровень 0–5 и преобразует его через `WeatherFromWaveLevel()`. |
| `GenerateBookingCount(rate, decay, future_offset)` | Проверяет неотрицательность аргументов, рассчитывает `λ = rate × exp(-decay × offset)` и берёт число заявок из распределения Пуассона. |
| `GenerateShipSpec(booking_day, planned_arrival_day)` | Выбирает тип с весами 0,58/0,27/0,15; случайную массу в диапазоне типа; стоянку 2–7 и терпение 2–9 дней; создаёт имя и незаполненные фактическую дату/задержку. |
| `GenerateActualArrivalDay(spec, config, earliest_possible_day)` | Равномерно выбирает целочисленное отклонение в заданном диапазоне и ограничивает итог снизу днём, когда заявка уже существует. |
| `GenerateUnloadingDelay(config)` | Равномерно выбирает неотрицательное число дней из диапазона конфигурации. |

Диапазоны масс различаются: сыпучий груз 1500–9000 т, жидкий 1200–7000 т,
контейнерный 800–5000 т. Профили сезонов заданы массивом из шести весов:
зимой вероятность больших волн выше, летом — спокойной воды. Вызовы генератора
не кэшируют планы автоматически: `GenerateRandomParametersForDay()` намеренно
вызывает его каждый день для доступного горизонта. Один плановый день может
получить заявки и от сегодняшнего, и от более ранних дней регистрации.

### 3.7 Погода (`weather.h`, `src/weather.cpp`)

`WeatherFromWaveLevel(level)` отвергает уровень вне 0–5 и возвращает `Weather`.
Таблица работоспособности: 0 → 1,00; 1 → 0,94; 2 → 0,82; 3 → 0,62;
4 → 0,32; 5 → 0. Флаг `storm` включается с уровня 4. Кран при уровне 5
всегда выполняет ноль тонн, даже если вручную задана положительная
работоспособность. При прочих уровнях `DailyThroughput()` использует именно
значение `weather.operability`, поэтому ручной сценарий может отличаться от
стандартной таблицы.

### 3.8 `Statistics` (`statistics.h`, `src/statistics.cpp`)

Класс только накапливает измерения и не решает, кто попадёт к крану.
`RecordArrival()`, `RecordRejection()`, `RecordAbandonment()` увеличивают
соответствующие счётчики на единицу. `RecordQueueLength(length)` добавляет
дневной замер, увеличивает число замеров и обновляет максимум.
`RecordCompletion(record)` копирует запись в `completions_`, добавляет дни
ожидания и задержки к суммам, обновляет максимумы и денежные итоги. Метод
`set_unfinished_ships(count)` сохраняет остаток после окончания месяца; он
вызывается из `Finalize()`, а не каждый день.

Все публичные читатели:

| Метод | Возвращаемое значение и знаменатель |
|---|---|
| `arrived_ships()` | Сколько судов фактически пришло, включая отклонённые. |
| `completed_ships()` | Размер вектора завершённых операций. |
| `abandoned_ships()` | Сколько ушло после ожидания. |
| `rejected_ships()` | Сколько не принято из-за вместимости. |
| `unfinished_ships()` | Сколько осталось при финализации. |
| `average_queue_length()` | Сумма дневных длин очереди / число дневных замеров; 0 без замеров. |
| `maximum_queue_length()` | Самая длинная очередь после обработки дня. |
| `average_waiting_days()` | Сумма дней ожидания / число завершённых разгрузок; 0 без них. |
| `maximum_waiting_days()` | Максимальное ожидание среди завершённых разгрузок. |
| `average_unloading_delay_days()` | Сумма дополнительных задержек / число завершённых разгрузок. |
| `maximum_unloading_delay_days()` | Максимальная дополнительная задержка среди завершённых. |
| `gross_revenue()` | Сумма начислений с коэффициентом ожидания до штрафов. |
| `total_penalties()` | Сумма штрафов за лишние дни стоянки. |
| `net_revenue()` | Сумма начислений за вычетом штрафов. |
| `service_rate()` | Завершённые / прибывшие; если никто не прибыл, возвращает 1. |
| `completions()` | Константная ссылка на детальные записи завершённых операций. |

Средние ожидание и задержка относятся только к **обслуженным** судам. Не стоит
интерпретировать их как средние для всех прибывших: отказавшиеся и ушедшие без
разгрузки в знаменатель не входят. Длина очереди, напротив, измеряется раз в
симулируемый день после прибытия, ухода, назначения и разгрузки.

### 3.9 `PortSimulation` (`port_simulation.h`, `src/port_simulation.cpp`)

Это главный объект состояния месяца. Он содержит копию `SimulationConfig`,
`RandomGenerator`, текущий день, следующий ID, рейтинг, признак финализации,
три `ShipQueue`, парк кранов, список запланированных судов, активные операции,
погодный план и `Statistics`. Начальный день равен 1, рейтинг — 100. Поле
`weather_by_day_` имеет размер `simulation_days + 1`, поскольку дни индексируются
с единицы. `ActiveUnloading` хранит судно, указатель на кран, день начала,
оставшиеся тонны, остаток задержки и признак окончания физической разгрузки.

#### Создание и планирование

- `PortSimulation(config)` копирует правила, инициализирует генератор seed-ом,
  создаёт пустой календарь погоды, вызывает `ValidateConfig()` и `BuildCranes()`.
- `ValidateConfig()` проверяет положительную длительность, шаг 1–3, ненулевую
  парковку, неотрицательные количества кранов/причалов/цены и корректный порядок
  диапазонов. Некорректность приводит к `invalid_argument` до запуска модели.
- `BuildCranes()` создаёт по массивам конфигурации типизированные краны, имена
  вида `CRANE-тип-номер` и уникальные ID. Краны существуют весь месяц.
- `ScheduleShip(spec)` проверяет имя, дни, массу, стоянку и терпение; при
  незаполненных полях генерирует прибытие и задержку, создаёт конкретный `Ship`,
  сохраняет его в расписании и возвращает ID. После `Finalize()` бросает
  `logic_error`. Фиксированное прибытие не может предшествовать регистрации.
- `SetWeather(day, weather)` сохраняет ручную погоду только для текущего или
  будущего дня в пределах месяца. Проверяет уровень 0–5 и коэффициент 0–1.
- `GenerateRandomParametersForDay(day, horizon)` проверяет день и горизонт 1–7.
  Если погодный план на этот день пуст, генерирует погоду. Затем для каждого
  планового дня от `day` до ограниченного концом месяца `day+horizon-1`
  выбирает число новых заявок и вызывает `ScheduleShip()` для каждой.

#### Дневной цикл и его внутренние шаги

- `SimulateDay()` отказывается работать после конца месяца или финализации.
  Если погода не задана, генерирует её. Создаёт `DailyReport`, вызывает этапы
  прибытия, ухода, назначения и разгрузки в указанном порядке, замеряет очередь,
  собирает строки для очередей и активных операций, снижает рейтинг за долгое
  ожидание, увеличивает `current_day_` и возвращает отчёт за завершённый день.
- `ProcessArrivals(report)` проходит расписание и извлекает суда, чей
  фактический день наступил. Поступившее судно учитывается в статистике.
  При заполненной **общей** парковке оно получает `kRejected`, запись ухода,
  событие и снижение рейтинга; иначе переходит в очередь своего типа.
- `ProcessAbandonments(report)` для каждой очереди применяет `RemoveIf()` к
  условию `current_day - actual_arrival_day >= max_wait_days`; ушедшие получают
  `kAbandoned`, запись ухода, событие, счётчик и снижение рейтинга.
- `AssignWaitingShips(report)` для каждого типа ищет свободный причал и кран.
  `ExtractBest()` выбирает судно по текущему `PriorityScore()`. Метод занимает
  кран, сохраняет активную операцию с полным остатком массы и задержкой и
  увеличивает `started_unloading`. Число одновременных операций ограничено
  `unloading_places[type]` и фактически свободными кранами.
- `ProcessUnloading(weather, report)` вычитает дневной объём из остатка каждой
  активной операции. Когда груз кончился, начинает отсчёт дополнительной
  задержки. При завершении вычисляет денежную запись, добавляет уход для карты,
  освобождает кран, пополняет статистику и отчёт, может поднять рейтинг за
  короткое ожидание и удаляет операцию. Операция, у которой груз закончился
  сегодня и есть задержка, начинает уменьшать её на **следующий** день.
- `CompleteUnloading(unloading)` не изменяет модель; рассчитывает даты,
  ожидание, общую стоянку, сверхплановые дни, начисление и штраф и возвращает
  заполненный `CompletionRecord`.

#### Помощники решения

- `FindAvailableCrane(type)` возвращает первый свободный кран нужного типа
  или `nullptr`. Порядок кранов стабилен, поэтому один и тот же парк даёт
  воспроизводимые индексы причалов на визуальном снимке.
- `ActiveCount(type)` считает текущие операции типа и нужен для лимита
  разгрузочных мест.
- `PriorityScore(ship)` объединяет потенциальный доход с бонусом за дни
  ожидания. При оставшемся терпении ≤1 добавляет срочный бонус `5e14`; после
  порога справедливости добавляет `1e15` и ещё `1e9` за каждый день.
- `RevenueMultiplier(waiting_days)` возвращает 1,12 при нуле дней, 1,06 при
  одном и далее `max(0,55, 1 - 0,04 × (waiting_days - 1))`.
- `AdjustRating(delta)` прибавляет изменение и ограничивает рейтинг 0–100.
  Изменения вызываются в точках отказа, ухода, завершения и при долгой очереди.

#### Завершение и чтение

- `RunRandomMonth()` повторяет генерацию и `SimulateDay()` до конца месяца,
  затем вызывает `Finalize()`. Используется консолью и оптимизатором.
- `Finalize()` один раз сохраняет число судов в очередях и активных операциях,
  помечает модель закрытой. Повторный вызов безопасен.
- `VisualSnapshot()` копирует все ожидающие и разгружаемые суда в `ShipView`.
  Для ожидающих остаток равен полной массе и `berth=-1`. Для разгружаемых
  вычисляет порядковый номер своего крана среди кранов того же типа и остаток
  массы не ниже нуля. Этот метод не содержит анимационной логики.
- `current_day()` возвращает **следующий** день обработки: после отчёта за
  день N вернёт N+1. `rating()` возвращает текущую репутацию.
- `waiting_ship_count()` суммирует размеры трёх очередей;
  `active_unloading_count()` читает число текущих операций;
  `scheduled_ship_count()` читает число ещё не прибывших судов.
- `CranePurchaseCost()` суммирует число кранов каждого типа × его цену.
  Эта сумма не вычитается из `Statistics::net_revenue()` автоматически.
- `config()` и `statistics()` возвращают константные ссылки на правила и
  статистику, не позволяя клиенту менять их в обход методов модели.

### 3.10 `CraneOptimizer` (`crane_optimizer.h`, `src/crane_optimizer.cpp`)

`OptimizationOptions` задаёт максимум количества каждого вида кранов и число
прогонов на конфигурацию. `OptimizationResult` хранит конкретный набор, цену
покупки, средние прибыль, рейтинг, долю обслуживания, срок окупаемости и флаг
соблюдения ограничений. `OptimizationReport` хранит все результаты и выбранный.

Статический `CraneOptimizer::Optimize(base_config, options)` проверяет
положительность максимумов и числа прогонов, затем перебирает **от 1** до
заданных максимумов для каждого типа. Для каждого кандидата создаёт несколько
независимых `PortSimulation`, прогоняет случайный месяц, суммирует и усредняет
итоги. Для одинакового номера испытания все кандидаты получают один seed:
`base_config.random_seed + trial`, что делает сравнение менее зависимым от
случайных различий. Результат после инвестиций — средняя операционная прибыль
минус стоимость покупки. Окупаемость — цена / положительная месячная прибыль;
при нулевой или отрицательной прибыли используется бесконечность.

Метод сортирует все варианты по результату после инвестиций. `best_result`
выбирает максимальный результат среди прошедших границы рейтинга и обслуживания.
Если таких вариантов нет, возвращает лучший денежный вариант без ограничений;
его `meets_quality_limits=false` сообщает вызывающему коду причину выбора.
В GUI есть отдельная локальная функция `FindCraneConfiguration()` с другим
критерием: минимальная цена среди допустимых вариантов из диапазона 0–5.
Эти два поиска нельзя считать эквивалентными и менять один, ожидая изменения
другого. Причалы не увеличиваются автоматически ни в одном из них.

## 4. Бэкенд: алгоритм дня и экономика

### 4.1 Порядок событий в `SimulateDay()`

```text
погода дня → приход → отказ при переполнении → уход по терпению
            → назначение кранов → выработка/задержка/завершение
            → длина очередей и списки → штраф рейтинга за старые очереди
            → current_day += 1
```

Эта последовательность объясняет несколько неочевидных наблюдений. Судно с
`max_wait_days=0` может прибыть и тут же уйти до назначения крана. Новое судно
может получить кран и начать разгружаться в день прибытия, если не исчерпало
терпение и есть ресурсы. Освобождение крана после завершения происходит позже
этапа назначения, поэтому свободное место используется со следующего дня.
В отчёте `waiting` и `unloading` уже отражают конец обработанного дня.

### 4.2 Расписание и очередь

Для заявки, созданной в день D на плановый день P, генератор выбирает
целочисленное отклонение `δ`, после чего фактический день равен
`max(P+δ, D)`. Генерация на горизонте до семи дней не гарантирует, что
заявки приходят в том же порядке, в каком создавались. Очередь физически
сохраняет порядок добавления, но кран получает заявку с максимальным
`PriorityScore()`. При равных оценках `ExtractBest()` оставляет более раннюю
в очереди. Три очереди разделены по виду груза, вместимость парковки общая.

Обычный рейтинг приоритета — базовая выручка плюс `waiting_days ×
waiting_priority_bonus`. Бонусы срочности и справедливости на порядки выше
базовой выручки. Поэтому приближение срока ухода обычно перебивает дорогой
груз, а судно после `fairness_wait_days` защищено от долгого голодания.
При переполнении парковки судно не попадает ни в одну очередь и учитывается
в `rejected_ships()`. Уход по терпению учитывается в `abandoned_ships()`.

### 4.3 Физическая разгрузка

Номинальная производительность крана в тоннах за день умножается на
`weather.operability`; при волнах уровня 5 принудительно равна нулю.
Остаток может стать отрицательным внутри операции после последнего дня, но
`VisualSnapshot()` ограничивает его нулём. Флаг `cargo_finished` отделяет
окончание физической работы от дополнительной задержки. Во время задержки
кран всё ещё занят: `Release()` вызывается только в момент полного
завершения операции. Это влияет на пропускную способность и штрафы.

### 4.4 Денежный результат

```text
base_revenue       = weight_tons × revenue_per_ton
waiting_days       = unloading_start_day - actual_arrival_day
total_port_days    = completion_day - actual_arrival_day + 1
extra_port_days    = max(0, total_port_days - planned_stay_days)
credited_revenue   = base_revenue × RevenueMultiplier(waiting_days)
penalty            = extra_port_days × penalty_per_extra_day
net_revenue        = credited_revenue - penalty
investment_result  = Statistics::net_revenue() - CranePurchaseCost()
```

Раннее обслуживание повышает оплату: множитель 1,12 без ожидания и 1,06
после одного дня. Начиная со второго дня действует линейное уменьшение, но
ниже 0,55 множитель не опускается. Штраф считается за **общее** время в порту,
а не только за дни разгрузки. Ожидающие и неразгруженные суда не создают
`CompletionRecord` и не приносят модельной выручки. Рейтинг 0–100 ведётся
отдельно от денег: отказ снижает его на 1,5, уход на 2,5; успешная разгрузка
прибавляет 0,8 при нулевом ожидании или 0,3 при ожидании до двух дней.
Каждое судно, которое продолжает ждать после порога справедливости, уменьшает
рейтинг на 0,05 в конце дня.

### 4.5 Исключения и границы корректности

Большинство недопустимых входных значений приводит к `invalid_argument`.
Попытка моделировать день после конца месяца даёт `out_of_range`, а
повторное занятие крана — `logic_error`. `PortSimulation` не является
потокобезопасным: GUI и CLI вызывают его последовательно в одном потоке.
Случайный генератор должен получать тот же порядок вызовов, если нужна
побитовая воспроизводимость. Время GUI, плавность кадров и скорость
проигрывания не меняют формулы дневного расчёта.
